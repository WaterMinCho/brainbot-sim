# 00. 큰 그림 — 로봇 소프트웨어와 시뮬레이터

## 로봇 소프트웨어는 루프다
실제 로봇의 소프트웨어는 세 단계를 초당 수십에서 수백 번 되풀이한다.

```text
센서 읽기 (Sense) → 판단 (Plan) → 구동 명령 (Act) → 다시 센서 읽기
```

| 단계 | 하는 일 | 예 |
|---|---|---|
| Sense | 세상의 상태를 숫자로 받는다 | 라이다 거리값, 바퀴 회전량, 카메라 영상 |
| Plan | 무엇을 할지 정한다 | "앞에 벽이 있으니 왼쪽으로 돈다" |
| Act | 모터에 명령을 보낸다 | 전진 속도 0.2 m/s, 회전 속도 0.5 rad/s |

이 프로젝트에서는 Plan을 맡는 코드를 **브레인**이라고 부른다. 규칙, 경로계획 알고리즘, 학습된 모델이 모두 브레인이 될 수 있다.

## 시뮬레이터가 하는 일
시뮬레이터는 **세상과 로봇의 몸을 대신한다.** 브레인은 그대로 두고 센서와 모터 너머를 소프트웨어로 바꿔 끼운다.

| 실제 로봇 | 시뮬레이터 | 마일스톤 |
|---|---|---|
| 모터가 바퀴를 돌려 로봇이 움직인다 | 명령 속도와 Δt로 다음 위치를 계산한다 (기구학) | M1 |
| 벽에 부딪히면 멈춘다 | 도형이 겹치는지 검사한다 (충돌 판정) | M3 |
| 라이다가 레이저를 쏜다 | 가상의 광선과 벽의 교점을 계산한다 (레이캐스팅) | M4 |

틱 한 번에 하는 일:
1. 브레인에게 센서 값을 주고 명령을 받는다.
2. 명령과 Δt로 로봇의 상태를 갱신한다.
3. 새 상태로 센서 값을 다시 만든다.
4. 화면에 그린다.

## React와 무엇이 같고 다른가
| | React 앱 | 시뮬레이터 |
|---|---|---|
| 상태가 바뀌는 계기 | 이벤트 (클릭, 응답 도착) | 시간. 아무 일이 없어도 틱마다 바뀐다 |
| 갱신 주기 | 필요할 때 | 고정 Δt (예: 1/60초) |
| 그리기 | 상태의 함수, `UI = f(state)` | 같다. 그리기는 상태를 읽기만 한다 |
| 시간 | 거의 신경 쓰지 않는다 | 모든 계산에 Δt가 들어간다 |

`UI = f(state)`는 그대로 가져온다. 갱신과 그리기를 나누는 것이 이 프로젝트 구조의 중심이고, 이미 익숙한 사고방식이다.

## 왜 고정 Δt인가
프레임 간격은 컴퓨터 상태에 따라 흔들린다. 그 값을 물리 계산에 그대로 쓰면 같은 브레인이 실행할 때마다 다르게 움직인다.
재현이 안 되면 디버깅도, 테스트도, 학습도 할 수 없다. 그래서 물리는 고정 간격으로 돌리고 그리기만 가변으로 둔다. M2에서 직접 구현한다.

## 이 프로젝트의 계층
```text
brains (판단)   ─┐
                 ├─→  core (세상, 로봇, 센서)
gui (화면)      ─┘
ros_bridge (M9) ─→  core
```
화살표는 의존 방향이다. core는 아무것도 모른다. 그래서 화면 없이 테스트할 수 있고, 나중에 화면을 바꾸거나 ROS2를 붙여도 core는 그대로다.

## 실제 로봇으로 옮길 수 있으려면
브레인은 센서 값과 명령만 다뤄야 한다. 시뮬레이터 안의 참값(로봇의 진짜 위치, 벽의 좌표)을 몰래 읽으면 실제 로봇에서는 동작하지 않는다.
실제 로봇은 자기 위치를 모른다. 바퀴 회전량과 센서로 추정할 뿐이다. 이 구분은 M5에서 인터페이스로 강제한다.

## 현업의 시뮬레이터
| 도구 | 특징 |
|---|---|
| Gazebo | ROS와 함께 가장 널리 쓰인다. 3D, 물리 엔진 |
| NVIDIA Isaac Sim | 사실적인 렌더링, 학습용 데이터 생성, 디지털 트윈 |
| MuJoCo | 빠른 물리 계산. 강화학습 연구에 많이 쓰인다 |
| Webots | 교육과 연구용 |

이 도구들은 M1~M4에서 직접 만드는 것을 대신 해 준다. 직접 만들어 보면 그 도구의 설정값이 무엇을 뜻하는지 알게 된다.
